# fixtures

Test corpora for Recueil's importers, exporters and ingestion pipeline: a synthetic Zotero library
and its storage directory, a Better BibTeX citation-key store, hand-written BibTeX, RIS and CSL-JSON
files, and — for Phase 2 — scans, mail, archives, a Paperless-ngx export and a set of ingestion
rules.

Phase 1's exit criterion is the author's own Zotero library imported at 100 % item count
(`CONCEPT.md` §7). That library is not in this repository and never will be, so the importer has to
be provable against something else. This directory is that something else: a library built from
Zotero's own schema, deliberately awkward in the ways a fifteen-year-old library is awkward, with
every count stated in advance so a test can assert against a number rather than against whatever the
importer happens to produce.

Phase 2's corpora (§§8–14) are built the same way and to the same rule. Every file is generated by a
committed script, every count is written by hand before the generator runs, and — because a
generator that checks its own output with its own code proves nothing — each corpus is read back by
a parser that had no part in writing it: pdf.js for the PDFs, Python's `email` for the messages,
Python's `zipfile` for the archives. Nothing is downloaded and nothing copyrighted is redistributed.

```
fixtures/
  expected-counts.json      every count in this document, machine-readable
  make-ingest.mjs           the Phase 2 generator
  lib/
    text-fixtures.mjs       counts and checks the BibTeX / RIS / CSL-JSON files
    ingest-fixtures.mjs     the Phase 2 promise, and the code that refuses to publish it unmet
    oracles.mjs             the independent parsers the Phase 2 corpora are read back with
    font-5x7.mjs raster.mjs  a bitmap font and a greyscale canvas, so a scan can be pixels
    pdf.mjs mime.mjs zip.mjs the writers — multi-page PDFs, RFC 5322 messages, hostile zips
    assets.mjs              the documents that appear in more than one corpus
    scans.mjs mail.mjs archives.mjs paperless.mjs rules.mjs   the five corpus definitions
  zotero/
    make-fixture.mjs        the Phase 1 generator
    lib/                    the generator's modules, including the library definition
    schema/                 vendored upstream schema + SOURCES.md (provenance)
    zotero.sqlite           generated — a real Zotero database
    better-bibtex.sqlite    generated — Better BibTeX's citation-key store
    storage/<KEY>/…         generated — the files the stored attachments point at
    linked-attachments/…    generated — the one linked file that resolves
  bibtex/                   6 hand-written files
  ris/                      3 hand-written files
  csl-json/                 3 hand-written files
  zotero-connector/         verbatim upstream excerpts, captured at pinned commits
  scans/                    generated — 6 PDFs; four have no text layer, two do
  mail/                     generated — 8 .eml files
  archives/                 generated — 3 zips, one of which must be refused
  paperless/                generated — a Paperless-ngx API dump, a route table and 11 originals
  rules/                    generated — rule files and the case table they are asserted against
```

`zotero-connector/` is a different kind of fixture from the rest of this directory: not something
generated here, but excerpts of Zotero's and the Zotero Connector's own source, captured at pinned
commits and used as the *oracle* for ADR-0006's compatibility claims. `apps/server` evaluates them
and runs the extension's real response-handling code over the server's real responses, so a shape
Recueil gets wrong fails with the error the browser would raise. Provenance, line ranges and the
re-capture commands are in `zotero-connector/README.md`.

## 1. Regenerating

Two generators, one manifest.

```sh
node fixtures/zotero/make-fixture.mjs     # the Zotero library and the format fixtures
node fixtures/make-ingest.mjs             # scans/, mail/, archives/, paperless/, rules/
```

The first rewrites `zotero.sqlite`, `better-bibtex.sqlite`, `storage/`, `linked-attachments/` and
`expected-counts.json`; the second rewrites the five Phase 2 directories and replaces the `ingest`
key of `expected-counts.json`. Each carries the other's keys forward rather than rewriting the whole
document, so they can be run in either order — but the file has to exist before `make-ingest.mjs`
can edit it, which means the Zotero generator runs at least once first. Both are deterministic and
both refuse to finish if a count has moved.

The rest of this section is about the Zotero generator; `make-ingest.mjs` is in §14, and its options
are the same three plus `--no-oracle`.

The generator needs a SQLite driver and finds one of two: `better-sqlite3`, resolved out of
`packages/core/node_modules` after a `pnpm install` at the repository root, or `node:sqlite`, which
needs no install but is only unflagged from Node 23. `better-sqlite3` is preferred so that a plain
`node` invocation works on the Node 22 LTS the project targets.

It is **deterministic**. Object keys are derived from a hash of each record's slug rather than
generated randomly, timestamps are literals, and the generated PDFs contain no clock. Running it
twice on the same machine produces byte-identical files, so a diff in `expected-counts.json` always
means something real moved — and if what moved was the vendored Zotero schema, that is exactly the
signal the importer needs.

Byte-identity holds per SQLite build, not across them: `better-sqlite3` 12.x (SQLite 3.53.2) and
this machine's `node:sqlite` (3.53.3) lay the pages out slightly differently. The *contents* are
identical — every row of every table hashes the same — so the fixture is the same fixture either
way, but do not diff the file across driver versions and expect nothing. Set
`RECUEIL_FIXTURE_SQLITE=node:sqlite` to force the fallback driver and check that for yourself.

Options:

| Option | Effect |
|---|---|
| `--out=DIR` | write somewhere other than `fixtures/zotero/` (then `expected-counts.json` is left alone) |
| `--id-layout=legacy` \| `fresh` | which numeric identifier layout to build; see §3 |
| `--no-counts` | build but do not touch `expected-counts.json` |
| `--check` | write nothing; rebuild into a temporary directory and report whether what is committed still matches. Exits 1 if it does not |
| `--quiet` | print nothing on success |

`--check` is the drift guard, and both generators have one. Worth a CI step:

```sh
node fixtures/zotero/make-fixture.mjs --check
node fixtures/make-ingest.mjs --check
```

It compares by content, not by bytes — every row of every table, the manifest, and the SHA-256 of
every generated file — so a different SQLite build is not a failure and an edited record is. It
touches nothing under `fixtures/`.

The generator refuses to finish if anything is off. It builds with foreign keys on and Zotero's own
triggers armed; it rejects a field or creator type that Zotero's global schema does not allow on the
item type; it reopens both databases from a fresh connection and runs `PRAGMA integrity_check` and
`PRAGMA foreign_key_check`; and it compares every count against the numbers hard-coded in
`zotero/lib/counts.mjs` and `lib/text-fixtures.mjs`, throwing on the first mismatch. Those hand-written
numbers are the promise; `expected-counts.json` is the receipt.

`make-ingest.mjs --check` does the same for the Phase 2 corpora, and compares by bytes: those files
have no page-layout variability to forgive. It also fails on a file that is committed under
`scans/`, `mail/`, `archives/`, `paperless/` or `rules/` and is not generated, so a stray file cannot
accumulate there unnoticed.

> **Note on `.gitignore`.** The repository root ignores `*.sqlite`. `fixtures/.gitignore` re-includes
> it, because here the SQLite files are committed artefacts rather than working data. The root
> pattern would be better written `/data/*.sqlite`; that file belongs to another part of the tree.

## 2. What the Zotero fixture is built from

Nothing is invented. `zotero/schema/` holds Zotero's and Better BibTeX's own files, copied verbatim,
with provenance and SHA-256 sums in [`zotero/schema/SOURCES.md`](zotero/schema/SOURCES.md).

| Piece | Source | Version |
|---|---|---|
| Table layout | `zotero/zotero` `resource/schema/userdata.sql`, tag `10.0.0` | userdata **129** |
| System tables and seeds | `resource/schema/system.sql`, same tag | system **32** |
| Triggers | `resource/schema/triggers.sql`, same tag | triggers **18** |
| Legacy identifier seed | `resource/schema/system-107.sql`, same tag | — |
| Item types, fields, creator types | `zotero/zotero-schema` `schema.json`, commit `b86c79b…` | globalSchema **45** |
| Citation-key store | `retorquere/zotero-better-bibtex` `content/db/citation-key.sql`, tag `v7.0.0` | — |

The database is assembled the way Zotero assembles one on a fresh profile
(`Zotero.Schema._initializeSchema`): `PRAGMA page_size = 4096`, then `system.sql`, `userdata.sql`,
`triggers.sql`, then a replay of `_updateGlobalSchema()` over the global schema, then
`_updateCustomTables()` to fill the `*Combined` tables — `itemData.fieldID` is a foreign key into
`fieldsCombined`, not into `fields`, so a fixture that skipped them would not be loadable.

`zotero.sqlite` is about 780 kB. Most of that is not data: Zotero's schema is 59 tables and 94
indexes and triggers, and at a 4 kB page size the root pages alone account for the bulk. Shrinking
the page size would shrink the file and stop it being what Zotero writes, so it stays.

Two things a real `zotero.sqlite` has that this one does not, both deliberate and both harmless:

- The `settings` row `('globalSchema', 'data')` — the zlib-deflated global schema — is written from
  a copy with the `locales` key removed, because the vendored `global-schema.json` drops it
  (254 kB of translated UI labels, none of which reaches a table). Everything Zotero actually reads
  out of that row at import time is present.
- Image annotations have no cached `annotation-<key>.png` under `storage/`. That cache is
  regenerable from the PDF and is not library data.

## 3. Two identifier layouts, and why it matters

`itemTypeID`, `fieldID` and `creatorTypeID` are **local** numbers. They never sync, and two Zotero
installations holding the same library can and do disagree about them, because Zotero allocates a
new one as `MAX(id) + 1` at the moment a type first appears (`Zotero.ID._getNext`). An importer that
hard-codes `itemTypeID = 4` for `journalArticle` is right on some libraries and wrong on others.

The generator can build both:

**`legacy` (the default, and what is committed).** Seeded from `system-107.sql` — the last revision
of Zotero's seed that carried the numeric rows — and then replayed forward through the four dates on
which item types entered the global schema, taken from the commit history of `zotero/zotero-schema`:

| Stage | Date | Adds | Resulting ids |
|---|---|---|---|
| seed | ≤ Zotero 4 | 36 types | `note` 1 … `dictionaryEntry` 36 |
| 1 | 2021-03-03 | `annotation` | 37 |
| 2 | 2022-03-03 | `preprint` | 38 |
| 3 | 2023-03-23 | `dataset`, `standard` | 39, 40 |

This is what a library carried forward from Zotero 4 holds today: `journalArticle` 4, `book` 2,
`bookSection` 3, `thesis` 7, `webpage` 13, `attachment` 14, `report` 15, `conferencePaper` 33.

Item-type identifiers are reproduced exactly. Field and creator-type identifiers are allocated by
the same algorithm but not against the same history — the fixture applies the *current* field
definitions at every stage, whereas a real library met each new field on the day it appeared. The
numbers are therefore plausible rather than provably identical to any one real library. That is the
point: an importer must resolve all three by name.

**`fresh`.** What Zotero writes on a brand-new profile: empty tables, one pass over the global
schema in its own (alphabetical) order, so `annotation` is 1, `artwork` 2, `book` 7,
`journalArticle` 22, and nothing lines up with the legacy layout at all.

```sh
node fixtures/zotero/make-fixture.mjs --id-layout=fresh --out=/tmp/zotero-fresh
```

A test that runs the importer against both and asserts the same result has proved the importer
resolves by name. The `fresh` build is not committed — it is one command and a few hundred
milliseconds — but the counts are identical to the committed build in every respect except
`zotero.itemTypeIds`.

## 4. The Zotero library, item by item

are derived as `sha256("recueil-fixture:item:<slug>")` folded into that alphabet, so they are stable
across regenerations and a test may hard-code one. The slug is not in the database; it is the handle
used in `zotero/lib/library.mjs` and in this document.

### 4.3 Citation keys — three sources, one conflict

`CONCEPT.md` §6 says the importer reads "Zotero 8 native citation keys or Better BibTeX keys from
`better-bibtex.sqlite` / Extra". The fixture has all three, disagreeing.

| Source | Count | Items |
|---|---:|---|
| Native `citationKey` field (Zotero 8+) | 3 | `ja-dedup-published` → `bianchi2023graph`, `ja-native-citekey` → `bianchi2024networks`, `ja-conflicting-keys` → `vasquez2020trace` |
| A `Citation Key:` line in `extra` | 2 | `ja-extra-citekey` → `schmidt2017soil`, `ja-conflicting-keys` → `vasquez2020traceelements` |
| `better-bibtex.sqlite` | 28 rows | 26 naming live items, 12 of them pinned |

`ja-conflicting-keys` carries all three, and all three differ (`vasquez2020trace`,
`vasquez2020traceelements`, `vasquez2020` — the last one pinned). The importer must pick one and the
verification report must say which and why. `ja-extra-citekey`'s Extra also carries a `PMID:` line
and a `tex.keywords:` line, so an Extra parser cannot simply take the first line.

Two Better BibTeX rows are **stale**: they name `itemID`s that are not in this library, which is
what Better BibTeX's own migration filters out (`content/key-manager/migrate.ts`). An importer that
does not filter them invents two items.

`better-bibtex.sqlite` is Better BibTeX's real schema: one table `citationkey(itemID, itemKey,
libraryID, citationKey, pinned)` with three indexes, built from upstream's own DDL with only the
`betterbibtex.` attach-name prefix removed.

that only ever existed on someone else's disk.

every file are in `expected-counts.json` under `zotero.storage.contents`, which is what an
attachment-hash coverage report can be asserted against.

cross-reference table (`pdftotext` extracts the title from all ten), and each snapshot is UTF-8 HTML
with a declared charset. None of them contains anything but generated text — no copyrighted material
is redistributed here.

### 4.5 Relations

Stored in `itemRelations` as URIs, not keys, because the library has never synced: the object of a
row is `http://zotero.org/users/local/v3aG8nQf/items/<KEY>`, where `v3aG8nQf` is the `localUserKey`

- **`dc:relation`, 11 rows.** Zotero writes both directions, and the fixture keeps that symmetry:
  the preprint/article/dataset triangle (`pp-dedup-preprint`, `ja-dedup-published`,

- **`owl:sameAs`, 1 row.** `rp-ipcc-ar6` points into a group library

- **`dc:replaces`, 1 row.** `ja-interop-jis` is the survivor of a merge and points at the key the
  merged-away item had.

## 5. BibTeX fixtures

Six hand-written files in `bibtex/`. Every one is small enough to read in full; the counts below are
checked on every generator run.

| File | Blocks | For |
|---|---|---|
| `awkward.bib` | 12 entries, 9 `@string`, 1 `@preamble`, 1 `@comment` | the main file, below |
| `crossref.bib` | 6 blocks: 2 containers, 1 `@xdata`, 3 children | inheritance |
| `files.bib` | 5 entries | the `file` field in four mutually incompatible dialects |
| `macros.bib` | 0 entries, 6 `@string` | a macro file with no entries at all |
| `uses-macros.bib` | 4 entries | entries whose `journal` is a macro defined in `macros.bib` |
| `malformed.bib` | 5 blocks | the error path |

**`awkward.bib`** covers, in order of appearance:

- Nine `@string` macros, four of them unused, and one (`jan`) that shadows a BibTeX built-in month
  macro — while `month = aug` and `month = jul` elsewhere use the built-ins that are *not* defined
  in the file.
- An `@preamble` with two `\newcommand`s and string concatenation inside it.
- An `@comment` block, which is not an entry. A parser that counts `@` finds thirteen entries here;
  there are twelve.
- LaTeX accent escapes — `{\"u}`, `{\'e}`, ``{\`e}``, `{\c c}`, `{\^o}`, `{\ss}` — *and* literal
  UTF-8 Greek and Cyrillic in the same file.
- Brace protection that must survive a title-casing style: `{DNA}`, `{SPARC}`, `{COAR}`,
  `{CO$_2$}`, `{Open Access}`, `{LaTeX}`, and single-letter protection like `{D}onau`, `{E}urope`.
- A multi-line `abstract` — five physical lines, one logical value, with the continuation indented.
- Value concatenation with `#`: `camb # ma` and `shortjournal = hessa`.
- `and others`, at the end of a fourteen-author list.
- Three name shapes in one `author` field (`king1963letter`): a suffix (`King, Jr., Martin Luther`),
  a braced corporate name (`{Weltgesundheitsorganisation}`), and a literal UTF-8 surname with a
  `\noopsort` sort-key command in front of it.
- An unbraced numeric value (`year = 1963`).
- A URL with percent-encoding, an ampersand and an underscore, unescaped.
- An entry with no `author` at all (`anon2021editorial`), and a `@misc` and an `@online` alongside
  the `@article`s and `@book`s.

**`crossref.bib`** has a forward reference on purpose: `bs-alpine` names `bk-hydrologie-3` before
that entry appears, so a single-pass resolver inherits nothing. It also mixes BibTeX's `crossref`
(field-by-field inheritance, and the container must carry `booktitle` for it to work) with
biblatex's `xdata` (whose block is not a citable entry).

**`files.bib`** carries the JabRef/Better BibTeX triple (`description:path:type`), a multi-file
value with a semicolon separator and an escaped colon inside a filename, Zotero's own bare absolute
path, Mendeley's brace-and-`$\backslash$:` form, and one entry whose `file` points at something that
is not there — alongside a `pdf` field, which some tools write instead.

**`malformed.bib`** is broken on purpose and is not expected to parse cleanly. Its five faults — an
unclosed brace, two missing commas, a duplicate entry key, an unbraced value containing `@`, and
trailing prose — are listed in a comment at the top of the file. The test question is not "does it
parse" but "does it recover, and does it name precisely what it could not read".

## 6. RIS fixtures

| File | Records | Encoding |
|---|---:|---|
| `awkward.ris` | 10 | UTF-8, **CRLF** |
| `endnote.ris` | 3 | UTF-8 **with BOM**, LF |
| `malformed.ris` | 3 `TY`, 3 `ER` | UTF-8, LF |

`awkward.ris` uses CRLF because that is what nearly every publisher's RIS export uses, and covers:
`JOUR`, `BOOK`, `CHAP`, `THES`, `RPRT`, `DATA` and `ELEC` types; a five-line continued `AB` field

`malformed.ris` has four records: one with no `ER`, one whose tag column is a character short

## 8. Scans — the OCR decision

`scans/` exists to answer one question: **does the pipeline know when it must OCR?** (CONCEPT §5.3
stages 4 and 5.) Six PDFs, built around the ways that question is got wrong. Every number below is
read back with pdf.js and is in `expected-counts.json` under `ingest.scans`.

| File | Pages | With a text layer | Rasterised | `/Rotate` | Why it is here |
|---|---:|---:|---:|---|---|
| `invoice-image-only.pdf` | 1 | 0 | 1 | 0 | the plain case: no text object anywhere, so OCR must run |
| `report-multi-page.pdf` | 3 | 0 | 3 | 0, 0, **270** | multi-page, and the last page was fed in sideways |
| `skewed-page.pdf` | 1 | 0 | 1 | 0 | rotated 0.055 rad (3.15°) **in the pixels**, so a deskew step has real work |
| `born-digital.pdf` | 2 | 2 | 0 | 0, 0 | a real text layer: OCR must be **skipped** |
| `mixed-text-and-scan.pdf` | 2 | 1 | 1 | 0, 0 | a born-digital letter with a scanned appendix |
| `sparse-text-layer.pdf` | 1 | 1 | 1 | 0 | a full page of raster under a **16-character** scanner stamp |

`report-multi-page.pdf`'s third page is captured **sideways** — the raster is landscape, 877 × 620
pixels on an 842 × 595 pt page, with the words running up it — and `/Rotate 270` is the correction. Both halves are needed. A `/Rotate` over an
upright raster would render crooked and recognise perfectly, which is the opposite of the case worth
fixturing; here, ignoring the page rotation hands the recogniser an image lying on its side, which
returns nothing, which is indistinguishable from a blank page.

The last two rows of the table are the ones that matter most.

**`mixed-text-and-scan.pdf`** is a letter typed in LibreOffice with a scanned laboratory sheet bound
in behind it. "Has a text layer" is a property of a *page*, not of a document; a per-document flag
either OCRs page 1 a second time or never OCRs page 2, and both are wrong.

**`sparse-text-layer.pdf`** carries the string `ADS-4700W 000412` — the scanner's own stamp — over a
page whose words are entirely pixels. A pipeline that skips OCR whenever `textCharacters > 0` loses
the page silently. This is the case OCRmyPDF's `--skip-text` / `--redo-ocr` split exists for, and
`ingest.scans['sparse-text-layer.pdf'].textCharacters` is pinned at exactly 16 so a threshold can be
asserted against it.

The pages are drawn, not photographed: a 5 × 7 bitmap font in `lib/font-5x7.mjs`, rasterised onto a
620 × 877 greyscale canvas with a seeded speckle, embedded as a Flate-compressed `DeviceGray` image
XObject. Nothing is downloaded and nothing copyrighted is redistributed. `pdftotext` over the three
wholly image-only documents returns nothing at all, which is the property the whole corpus rests on.

There is no OCR engine in this repository and none in CI. The corpus is therefore for testing the
*decision* and the plumbing around it, against a fake OCR adapter; it cannot test recognition
quality, and no test here should pretend to.

## 9. Mail

`mail/` is the corpus for the IMAP source in CONCEPT §5.3: "attachments as Documents, body as Note,
rules by sender/subject". Eight messages, each a different way for that sentence to go wrong. All
CRLF, as a `.eml` must be. Every number is read back with Python's `email` package.

| File | Type | Parts | Attachments | Why it is here |
|---|---|---:|---:|---|
| `plain-text.eml` | `text/plain` | 1 | 0 | quoted-printable UTF-8; the body is a Note and there is nothing else |
| `html-multipart.eml` | `multipart/alternative` | 3 | 0 | two representations of one body — only one of them is the Note |
| `two-attachments.eml` | `multipart/mixed` | 4 | 2 | one filename in `filename=`, one split across **three RFC 2231 continuations** |
| `inline-image.eml` | `multipart/related` | 4 | 1 | a `cid:` wordmark that is **not** an attachment, beside one that is |
| `forwarded-nested.eml` | `multipart/mixed` | 6 | 2 | a `message/rfc822` whose own multipart body carries a PDF two levels down |
| `subject-non-utf8.eml` | `text/plain` | 1 | 0 | **not a valid UTF-8 file** |
| `malformed-boundary.eml` | `multipart/mixed` | 2 | 0 | must be handled, not thrown on |
| `attachment-name-traversal.eml` | `multipart/mixed` | 7 | 5 | four hostile filenames and one legitimate |

**`subject-non-utf8.eml`** does three things at once, all of which happen in real mail. The Subject
is two adjacent RFC 2047 encoded words in ISO-8859-15 — one Q-encoded, one B-encoded — which RFC 2047
says are joined with no space between them, and the first carries a euro sign, whose byte `0xA4`
means `¤` in ISO-8859-1. The `From` display name is raw 8-bit windows-1252, which is illegal and
which every German mail server has seen this week. The body is 8-bit ISO-8859-15. A
`readFileSync(path, 'utf8')` anywhere in the mail path turns the Subject into replacement characters
and the body into mojibake, so `ingest.mail['subject-non-utf8.eml'].utf8Valid` is pinned at `false`
and the decoded Subject is pinned at `Zahlungserinnerung: 471,50 € offen (Kundennr. 88-201934)`.

**`malformed-boundary.eml`** declares `boundary=--=_Part_9182_1839` — unquoted, and beginning with two
hyphens, so the delimiter line is four hyphens and the header is ambiguous before anything else goes
wrong. The second part's delimiter is then two characters short, so it reads as body text rather than
as a part, and there is no closing delimiter at all — which is what a truncated IMAP fetch leaves
behind. Python recovers the first part and records a `CloseBoundaryNotFoundDefect`; that is the
correct behaviour and the manifest records the defect by name. Throwing is not.

**`attachment-name-traversal.eml`** carries five attachments: `../../../../etc/cron.d/recueil-pwn.pdf`,
`C:\Windows\Temp\recueil-pwn.pdf`, a name that is only `../../escape.pdf` *after* three RFC 2231
continuations are joined and percent-decoded, a `name=`-only `.bashrc` with no disposition at all, and
one legitimate `Invoice-88201934.pdf`. A filename that arrives in a header is hostile until it has
been resolved and checked to be inside its root. The legitimate one is there so that refusing the
message and refusing the four are distinguishable.

## 10. Archives

`archives/` is the corpus for CONCEPT §5.3 stage 3, "archive extraction (zip, eml) to scratch; inner
files re-enter at stage 1". Read back with Python's `zipfile`, `testzip()` included, and cross-checked
with `unzip`.

| File | Entries | Contents |
|---|---:|---|
| `mixed.zip` | 9 | PDFs and images in subdirectories, two directory entries, an empty file, one UTF-8 filename with general-purpose bit 11 set and one CP437 filename **without** it |
| `nested.zip` | 4 | two of its members are zips; the deepest chain is three archives |
| `path-traversal.zip` | 7 | one legitimate entry and six hostile ones |

**`mixed.zip`** carries `Grundriß.png` written in CP437 with bit 11 clear, which is what Windows
Explorer produced for twenty years. Python's `zipfile` decodes it as `Grundri▀.png`; a reader that
assumes UTF-8 gets an invalid sequence; a reader that assumes Latin-1 gets a third answer. All three
are wrong to *guess*, and the fixture is here so that whatever the extractor does, it does on
purpose. The same file's `Ordnerübersicht.txt` is UTF-8 with the flag set, so both conventions are in
one archive.

**`nested.zip`** contains `innen.zip` (which holds a copy of the invoice, two levels down) and
`tiefer/noch-tiefer.zip` → `innerste.zip` → `ende.txt`, three archives deep. A pipeline that re-enters
inner files at stage 1 has to decide where to stop; `ingest.archives['nested.zip'].maxArchiveDepth` is
`3`, so a test can assert the cap fires with a reason rather than that the extractor recurses until
the scratch space runs out.

**`path-traversal.zip` must be rejected safely**, and the shape of "safely" is the point:

| Entry | Why it is refused |
|---|---|
| `harmlos.txt` | **it is not** — this is the legitimate one |
| `../../../../tmp/recueil-pwned.txt` | a relative climb |
| `/etc/recueil-pwned.txt` | absolute; `path.join(root, name)` discards the root entirely |
| `..\..\recueil-pwned-win.txt` | backslash separators — harmless on Linux, a climb on Windows |
| `unterordner/../../escape.txt` | only a climb *after* normalisation; `startsWith()` on the raw name passes it |
| `.././.././recueil-pwned-dots.txt` | the same climb spelled with single-dot segments |
| `link-nach-etc-passwd` | a **symbolic link** to `/etc/passwd`: the name is ordinary, the mode is not |

Five are caught by looking at the name and the sixth only by looking at the external attributes. A
fixture with nothing but hostile entries cannot tell "refused the archive" from "refused the entries",
so `harmlos.txt` is there and must survive.

These names are written by `lib/zip.mjs` rather than by an archiving library, because every archiving
library worth using refuses to write at least three of them.

## 11. Paperless

`paperless/` is a Paperless-ngx API export, for CONCEPT §6: "API export of documents, tags,
correspondents, document types, custom fields, ASN + originals → Office facet". Eleven live documents,
one in the trash, eleven original files, ten JSON responses and a route table.

**What it claims, and what it does not.** It reproduces the *shapes* Paperless-ngx 2.x serialises: the
`count` / `next` / `previous` / `all` / `results` envelope, the `matching_algorithm` integers,
`custom_fields` as `{value, field}` pairs, monetary values as `"EUR471.50"` strings,
`archive_serial_number`, `deleted_at`, and the separate `/api/trash/` collection. It is written from

can be compared when it exists.

## 12. Rules

`rules/` is the corpus for CONCEPT §5.3 stage 8, the rule engine: "match on source, sender, path, text
regex, resolver result → item type, collection, tags, custom fields".

**The schema is a proposal; the cases are the contract.** `spec/data-model.md` open decision O2 has
not been settled — rules may end up a table with YAML import/export, or files. The schema in these
files is a reading of CONCEPT §5.3 and of `rule_ref` in §4.9, not a specification, and if the Phase 2
ingestion spec settles on something different, these files move. What does not move is
`rules/cases.json`: an input document, the rules that fire on it, in what order, and what comes out.
That table is written in terms of rule **ids** rather than of file syntax, so it survives a change of
format.

**The evaluation contract the corpus assumes**, stated in `cases.json` as well as here:

1. Rules are evaluated by `priority` descending, then by `id` ascending. Document order is not
   significant; a file is a set, not a script.
2. `enabled: false` rules are not evaluated at all, whatever their priority.
3. A rule whose `match` succeeds *fires*, and its actions are collected.
4. A fired rule with `stop: true` ends evaluation; nothing of lower priority is even examined.
5. Two fired rules that set the *same field* to *different values* apply neither: the document goes to
   the review queue with `reason_code = "rule_conflict"`. "Last one wins" is not the rule, because
   after (1) there is no last one.

| File | Rules | For |
|---|---:|---|
| `precedence.yaml` | 6 | a `stop`, a disabled rule at the very top, an equal-priority conflict, a floor |
| `precedence.json` | 6 | the same rule set in JSON, written independently rather than serialised |
| `negation.yaml` | 5 | `none`, including the empty one and the nested one |
| `hostile-regex.yaml` | 7 | patterns that must not be handed straight to a regex engine |
| `hostile-regex.input.txt` | — | the input that detonates them |
| `malformed.yaml` | 6 | valid YAML, invalid rule set, six faults |
| `cases.json` | 11 cases | the assertion table |

**`precedence.yaml`.** `disabled-catch-all` has priority 999 and `enabled: false`; a loader that sorts
before it filters, or that treats a missing `enabled` as false, turns every document in the corpus
into `other`. `invoice-stadtwerke` (100, `stop`) and `invoice-generic` (50) both match the Stadtwerke
invoice, and only the first may fire — the case table asserts that `invoice-generic` and
`catch-all-pdf` were **not evaluated**, which is a different statement from "did not match".
`tie-vertrag-a` and `tie-vertrag-b` sit at 60 and disagree about `item_type`, so the contract's rule 5
applies.

**`precedence.json`** is the same rule set typed out again rather than serialised from the YAML.
Loading both and comparing proves the loader agrees with itself across syntaxes; loading one and
serialising it to the other would have proved nothing.

**`negation.yaml`.** Two of its five rules are the ones a negation implementation gets wrong.
`vacuous-none-scanner` has an **empty** `none`, which is vacuously *true* — there is nothing to
exclude. Fold it with the wrong identity (`some()` over an empty list is `false`, and `not false` is
`true`, but `every()` is `true` and `not true` is `false`) and the rule is off for every document in
the library. `double-negative-storno` has a `none` nested inside a `none`, which means "the document
**is** tagged Storno"; an implementation that flattens nested negations gets the exact opposite
answer, silently.

**`hostile-regex.yaml`.** Three patterns backtrack catastrophically (`^(a+)+$`, `^(\w+\s?)*$`,
`(x+x+)+y`) against the 45-character lines in `hostile-regex.input.txt`. One (`^(unclosed`) is not a
regular expression at all and must be refused when the file is *loaded*, naming the rule — not at
match time, on the twelve-thousandth document. One is a backreference, which JavaScript compiles and
RE2 does not, so the engine must say which it is rather than compile something that never matches. One
is a PCRE inline flag, `(?i)rechnung`, on which `new RegExp` throws — treating the throw as "no match"
makes the rule quietly dead. One is `\p{Script=Greek}{4,}`, which without the `u` flag matches the
literal text `p{Script=Greek}` and nothing else: a wrong answer rather than an error.

The corpus does not say *how* an engine survives these. It says that loading the file and evaluating
every rule that compiled, against every line of the input, must finish, and it states a budget —
`budgetMilliseconds: 2000` — so a test can hold it to that.

**`malformed.yaml`** is valid YAML and an invalid rule set: no `version`, a rule with no `id`, two
rules sharing an id, a string where `priority` must be an integer, an action nobody defined, and a
condition key nobody defined. The faults are listed in a comment at the top of the file, as in
`bibtex/malformed.bib`, and the question is the same one: not "does it load" but "does it name all six,
or stop at the first". It also carries a YAML merge key, which some loaders honour and some do not —
not a fault, but something a loader has to decide about on purpose.

## 14. How the Phase 2 corpora are checked

A generator that checked its own output with its own code would prove nothing — the same
misunderstanding writes the file and passes the check. So each corpus is read back by something that
had no part in writing it, and the properties it reports are compared against numbers written by hand
in `lib/ingest-fixtures.mjs` before the generator ever ran.

| Corpus | Oracle | What it confirms |
|---|---|---|
| `scans/` | **pdf.js**, from `apps/web/node_modules` | page count, per-page text-item and character counts, image XObject operators, `/Rotate` |
| `mail/` | **Python's `email`** | content type, part structure, attachment filenames after RFC 2231 reassembly, the decoded Subject, the defect classes, and a SHA-256 per decoded part |
| `archives/` | **Python's `zipfile`**, `testzip()` included | entry names byte for byte, the UTF-8 flag, Unix mode, CRCs, and a SHA-256 per entry — recursing into inner archives |
| `rules/*.yaml` | the **`yaml`** package, from `packages/rules` | that `malformed.yaml` really is valid YAML, which is half of what it claims |

If any oracle is unavailable the build **fails**, and the reason is printed. `--no-oracle` produces a
receipt anyway, and says so: `ingest.oracles` records which readers ran, by name and version, so a
manifest that was produced without them cannot be mistaken for one that was not.

`unzip -t`, `pdfinfo` and `pdftotext` are not used by the build — they are not everywhere — but the
corpus is written so that they agree, and they are worth reaching for when something looks wrong.

| `zotero.notes`, `.attachments`, `.annotations` | §4.1, §4.4 — including `attachments.missing`, with a key and a reason for each |
| `zotero.collections`, `.tags`, `.creators`, `.relations` | §4.1 |

## 16. Using this from a test

```js
import { readFileSync } from 'node:fs';

const counts = JSON.parse(readFileSync('fixtures/expected-counts.json', 'utf8'));

// The Phase 1 exit criterion, in one assertion.
expect(report.items.imported).toBe(counts.zotero.items.regularLive);          // 64
expect(report.itemsByType.article).toBe(counts.zotero.liveByType.journalArticle); // 20

// The verification report has to name both broken attachments, and say why they differ.
expect(report.review.map((r) => r.itemKey).sort())
  .toEqual(counts.zotero.attachments.missing.map((m) => m.itemKey).sort());

// Attachment-hash coverage: Recueil's SHA-256 for every file the importer did find.
for (const file of counts.zotero.storage.contents) {
  expect(documents.get(file.sha256)).toBeDefined();
}
```

To prove the importer resolves item types by name rather than by number, build the other

against it — every count is identical, and not one numeric identifier is:

And for the ingestion pipeline:

```js
const ingest = counts.ingest;

// The OCR decision, per page. A document-level flag cannot satisfy this one.
const mixed = ingest.scans['mixed-text-and-scan.pdf'];
expect(plan.pagesToOcr('scans/mixed-text-and-scan.pdf'))
  .toEqual([2]);                                       // page 1 has a text layer, page 2 does not
expect(mixed.textLayerPages).toBe(1);

// The stamp is not a text layer.
expect(ingest.scans['sparse-text-layer.pdf'].textCharacters).toBe(16);

// The archive is refused entry by entry, not wholesale.
const traversal = ingest.archives['path-traversal.zip'];
expect(extracted.map((e) => e.name)).toEqual(['harmlos.txt']);
expect(refused.map((e) => e.name).sort())
  .toEqual(traversal.byEntry.filter((e) => e.hostile || e.symlink).map((e) => e.name).sort());

// One Document, six arrivals.
const invoice = ingest.sharedDocuments
  .find((d) => d.appearsAs.includes('scans/invoice-image-only.pdf'));
expect(documents.countByHash(invoice.sha256)).toBe(1);
expect(attachments.countByHash(invoice.sha256)).toBe(invoice.arrivals);   // 6

// The Paperless report names the unfetchable document — by comparing the two sides, not by
// counting its own log. `dump` is the fixture; `imported` is what the importer produced.
const dump = JSON.parse(readFileSync('fixtures/paperless/api/documents-page-1.json', 'utf8'));
const listed = new Set([...dump.all]);
const got = new Set(imported.map((item) => item.sourceId));
expect([...listed].filter((id) => !got.has(id)))
  .toEqual(ingest.paperless.documents.unfetchable.map((d) => d.id));       // [1007]

// And it does not import the trash.
expect(got.has(1008)).toBe(false);
```

The rule cases are their own table, keyed by rule id so that a change to the file syntax does not
invalidate them:

```js
const { cases } = JSON.parse(readFileSync('fixtures/rules/cases.json', 'utf8'));

for (const testCase of cases.filter((one) => one.expect.fired)) {
  const result = engine.load(`fixtures/rules/${testCase.ruleFile}`).evaluate(testCase.input);
  expect(result.fired.map((r) => r.id)).toEqual(testCase.expect.fired);
  expect(result.reviewReason ?? null).toBe(testCase.expect.reviewReason ?? null);
}
```

A test may serve `fixtures/paperless/` over an in-process HTTP server built from
`paperless/index.json` — `{ method, path, query, status, contentType, file }` per route — and point
the real importer at it. That is what makes "Paperless decommissioned after verified import"
(CONCEPT §7) testable with no container anywhere in the loop.

## 17. Still to come

Two gaps, both named rather than papered over.

**A recorded Paperless session.** §11 is a model of the API, not a capture of it. Until one real
session has been recorded against the instance that is being decommissioned, the corpus proves the
importer handles these shapes and nothing about whether they are the shapes that instance emits.

**Recognition quality.** There is no OCR engine in this repository and none in CI, so `scans/` tests
the decision to OCR and the plumbing around it, against a fake adapter. Whether OCRmyPDF reads
`Karlstraße 1, 89073 Ulm` off `invoice-image-only.pdf` is a question this corpus cannot answer, and
no test here should be written as though it could.
